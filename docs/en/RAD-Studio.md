# Integrating Atlas IDE Expert into RAD Studio

*Deutsche Fassung: [RAD-Studio.md](../RAD-Studio.md)*

There are two ways:

- **Recommended: the IDE plugin** `Atlas.IDE.Base` (ADR 0006) for RAD Studio 13 and 12. It registers as its own Code Insight manager and brings its own windows for completion, parameter hint and hover as well as problems in the editor, bracket pairs, command palette and compiler check (overview in the [README](../../README.md)).
- **Built-in LSP client** (section below). With it, outline and Error Insight work. However, RAD Studio does not show the hover of third-party servers this way.

## IDE plugin

**From the release package:** Extract `atlas-ide-expert-<Version>.zip` from the [release](https://github.com/xKnockOut/Atlas-IDE-Expert/releases) into a fixed folder (e.g. `%LOCALAPPDATA%\Programs\Atlas`) and register `Win32\Atlas.IDE.Base370.bpl` (64-bit IDE: `Win64\…`) as in step 2 below; the plugin finds the server one level above the BPL. Details in [Installation.md](Installation.md#rad-studio-release-package). The installer `AtlasSetup.exe` (up to 1.1.0) no longer exists since 1.2.0 ([ADR 0016](../adr/0016-kein-installer.md), German). The steps below are the way with your own build.

By hand:

1. Build the package `Packages\Atlas.IDE.Base\Atlas.IDE.Base.dproj` (contained in the project group) with the Delphi version it is to run in: **Win32** for the classic IDE, **Win64** for the 64-bit IDE (from Delphi 12.3). Result: `Output\Win32\Debug\Bpl\Atlas.IDE.Base370.bpl` or `Output\Win64\…`; the number is the package version (`370` Delphi 13, `290` Delphi 12). Once the plugin is installed, the IDE locks this BPL; unload the package before rebuilding.
2. In RAD Studio: *Component > Install Packages > Add*, select the BPL.
3. Build the server (`AtlasServer.exe`) as well: Common, Windows and Server for the same platform (Win64 recommended). The server is a separate program and does not depend on the Delphi version.
4. The plugin looks for the server in this order:
   - *Tools › Options › Third Party › Atlas*, field “Atlas server” (registry `HKCU\Software\Atlas\IdePlugin`, value `ServerPath`; optionally `ServerArguments`, e.g. `--log C:\Temp\atlas.log`). Below it the page shows which server is used and whether it was found.
   - `AtlasServer.exe` next to the BPL
   - `AtlasServer.exe` one level above the BPL (layout of the release package: `…\Atlas\Win32\Atlas.IDE.Base370.bpl`, `…\Atlas\AtlasServer.exe`)
   - `..\..\..\Win64\Debug\Bin\AtlasServer.exe`, otherwise `..\..\..\Win32\Debug\Bin\AtlasServer.exe`, i.e. the build output in the repo

If the server is missing, the plugin reports this in the Messages window and leaves completion and hints to the built-in Code Insight. If the server crashes, it restarts it on the next request.

The scope of the index is set in *Tools › Options › Third Party › Atlas* for all projects (#652): all projects of the project group, all units of the project search paths and all units of the Delphi library. The plugin passes the values to the server at startup and after every change. If `index` is set in a project's `atlas.json`, the file applies there. The server reads RTL, VCL and FMX once per Delphi version and platform, independently of the project's defines.

Index and cache (#492): The server stores the index per Delphi version and project under `%LOCALAPPDATA%\Atlas\Index\<Version>\<Projekt-Hash>\index-<Format>.atlasidx`, the library separately under `…\<Version>\Bibliothek\`. The file carries a format version and a checksum; if it is damaged or outdated, the server discards it with a line in the log and silently rebuilds it. Per declaration the index stores signature, directives (`virtual`, `overload`, `deprecated`, `platform`, …) and the XMLDoc summary, in project units also the usages of every identifier (can be switched off with “Index identifier usages”, registry `IndexUsages`, `index.usages`). When the memory limit is reached (field “Index memory limit”, registry `MemoryBudgetMb`, default 768, 0 = no limit), the server first swaps out the usages and reloads them from the cache when needed; only after that does it trim units. The “Symbol index” section of the options page shows units, declarations, memory, size on disk and the last update; the buttons rebuild the index or, after confirmation, delete all caches (`atlas.server.clearIndex`), after which the server indexes again. While the server is indexing, the Atlas field in the status bar is yellow (“Atlas · Index n %”), and completion notes “limited” in its footer.

Welcome page (#753, ADR 0011, 0014 and 0015): The Atlas welcome page is available in two places that can be switched independently.

- **IDE welcome page** (`welcomePage.ideWelcomePage`, default on): Every Atlas section is a welcome page plugin (ID `Atlas.Welcome.<Bereich>`) and can be moved and hidden with the IDE's own means. *Atlas › View › Apply Atlas layout* (`welcomePage.layout = atlas`) instead sets up a section “Atlas” with a header and all sections at the top across all columns; beforehand Atlas backs up the key `HKCU\Software\Embarcadero\BDS\<Version>\WelcomePage` to `%LOCALAPPDATA%\Atlas\welcomepage-layout-backup.json`, *Reset Atlas layout* writes it back exactly. If you switch off the IDE welcome page, Atlas removes its sections and tidies up the grid (restores the backup, otherwise removes all `Atlas.Welcome.*` entries and closes empty rows); the same happens at startup as long as it is off. If the IDE overwrites the grid on shutdown, Atlas repeats the desired state once at the next start (marker `welcomepage-layout-pending`).
- **“Atlas Start” window** (*View › Atlas Start*, also *Atlas › View › Atlas Start* and the command palette): opens on request, with “Open ‘Atlas Start’ when the IDE starts” (`welcomePage.openOnStart`, default off) and as soon as the last project is closed (`welcomePage.openWhenNoProject`, default on; not when the IDE shuts down). Everything can be set under *Tools › Options › Atlas › Welcome page* and switched off as a quick toggle.

New in Atlas (#756): After an update the welcome page shows, once, the card “New in Atlas <Version>” at the top with the new features of the skipped versions, each with keyboard shortcut, a toggle for the setting and “Try it” (command or sample file from `<Installationsordner>\Beispiele`). The source is `whatsnew.json` in the installation folder; the version seen is stored under `HKCU\Software\Atlas\IdePlugin` in `WhatsNewSeen`. Right-clicking into the Atlas sections offers “Show what's new in this version” and “All versions”; `welcomePage.whatsNew` (off, afterUpdate, always) controls the card.

Discover Atlas (#757): The card shows one tip per IDE start from `<Installationsordner>\tips.json` with an image from `Tipps\`, title, text, the actual shortcut from the command palette and “Never used” or “Last used 3 weeks ago”; “Try it” opens `Beispiele\Entdecken.pas` at the position given in `tips.json` or runs the command, “Next tip” pages on, “Don't show again” blocks the tip permanently. Order: enabled, never used features first (each start beginning after the tip shown last), then those unused for the longest time; a tip with `setting` appears only if that plugin setting is on (for a choice such as `WelcomePageWhatsNew`: not `off`), one with `command` only if the command palette shows the command; Atlas keys without a palette command (command palette, completion, parameter hint) show their key from the settings or the IDE's. “Try it” without a sample file runs `try`, otherwise `command` (for the tip about the command palette it opens the palette; for undo it opens the “Atlas changes” list instead of undoing immediately). `tips.json` has one tip for each command that can be discovered (28). Images: 320 × 180 logical pixels, at 100 % pixel for pixel, from 125 % taken from the file `<name>@2x.png` (640 × 360), converted once with HALFTONE if the size differs; from a column width of about 560 pixels the text sits next to the image, otherwise below it, and in narrow columns the image shrinks with the same aspect ratio. One image for light and dark theme; generated from `Tools/Tipps/Vorlagen` (see [Release.md](../Release.md#bilder-der-tipps), German). Usage is counted per command in `%LOCALAPPDATA%\Atlas\usage.json` (only ID, counter, date; the same count as the shortcut tips, #600); blocked tips and the tip shown last are stored in the `discover` section of `%LOCALAPPDATA%\Atlas\shortcut-tips.json`. `welcomePage.discover` switches off the card, `tips.usageTracking` the counting (then in sequence); “Reset usage count” and “Show blocked tips again” are on the *Welcome page* page.

Help and feedback (#766): The section sits at the bottom of the right column and has four buttons; “Support Atlas ♥” opens the donation page (PayPal) in the default browser, nothing is sent. “Atlas docs” opens `<Installationsordner>\Doku\index.html` (searched next to the BPL and one level above) in the default browser, without an installation the repository's documentation page. “Keyboard shortcuts” opens the overview from #520; with `keys.overview` off the button is greyed out. “Report a problem …” opens the dialog for the diagnostic package: checkboxes for logs (`%LOCALAPPDATA%\Atlas\Logs\atlas.log`, last 2000 lines, and the server's diagnostic logs of the last 7 days), versions, settings without paths and, if present, the latest diagnostic data (`Logs\Diagnose\atlas-diagnosemodus.txt`, #479); preview of every file; “Create ZIP” writes `Atlas-Diagnose-<Datum>.zip` (if necessary `-2`, `-3` …) to `welcomePage.help.reportFolder` (empty = desktop) and shows it selected in Explorer; “Open issue page” puts the template (description, versions, name of the ZIP) on the clipboard and opens `welcomePage.help.reportUrl` in the browser. Anonymisation works as for the error report (#108, #647): project roots, user, computer and domain name (from three characters) and paths are replaced. The short description only goes into the template, not into the ZIP. Atlas does not access the network and sends nothing; Explorer, clipboard and browser are opened only by a click.

Setting up a project for Atlas (#759): For the active project (without an open project the topmost one of the “Reopen” list) the welcome page shows the card “Set up XmlInspector for Atlas” as long as a step is open and nobody has chosen “Don't ask again for this project”. Completed steps are shown in green with ✓. Every step runs only on a click: “Create atlas.json” with a choice of template (“Existing project” as default, “New project, strict”, “Legacy project with baseline”; files `atlas-existing.json`, `atlas-strict.json`, `atlas-legacy.json` in the `Vorlagen` folder of the installation) checks the template against the schema, shows the content and, after “Create”, writes the file next to the `.dproj` or `.groupproj` (UTF-8 without BOM, CRLF; an existing `atlas.json` or `delphi-lsp.json` remains untouched). “Create baseline” takes the same route as *Update project baseline* (#97) and shows the running seconds; afterwards the new findings of the project summary are at 0. “Check search paths and defines” reads, in the background, the main file and all units of the project together with search paths, unit namespaces and defines of the active configuration and platform and the IDE's library paths; it reports units from `uses` that the compiler would not find (“Unit “Xml.Helpers” not found – Src\Main.pas, line 12”) and symbols from `{$IFDEF}` that neither the `.dproj` nor a `{$DEFINE}` sets. It substitutes `$(…)` in the paths like the IDE does: first the environment variables from *Tools › Options › Environment Variables*, the folders of the running IDE (`BDS`, `BDSLIB`, `BDSBIN`, `BDSINCLUDE`, `BDSCOMMONDIR`, `BDSUSERDIR`, `BDSCatalogRepository`), project (`ProjectDir`, `ProjectName`, `MSBuildProjectDirectory` …), `Platform` and `Config`, then the environment of the process. If a macro remains unknown, the path is dropped; missing units (without `in 'Pfad'`) then count as uncertain and appear as “… (uncertain, search path with unknown macro $(MEINLIB) skipped)” in the card without keeping step 4 open. For an open project group with several projects (or a `.groupproj` as target) “Check” checks every project of the group; the findings are stored per project in its summary, the card shows the total, the findings with project name and, as long as not all have been checked, “2 of 3 projects of the group checked”. A click on a finding or on “Project options …” opens the project options. Projects that are not open get the button “Open project” instead of “Start” and “Check”. Below that, “New with Atlas: unit, form, test class” open the create menu (#719) with the file templates of the kind (supplied: empty unit, unit with class, VCL form, DUnitX test class; your own code templates with `file: unit`, `file: form` or `file: test` in the header are added) and create the chosen one as a new, unnamed file in the active project. The state is stored in the `setup` section of `%LOCALAPPDATA%\Atlas\projects\<Schlüssel>.json`; *Set up project for Atlas* in the command palette (`Atlas.ProjectSetup`) asks again. `welcomePage.projectSetup` switches everything off (also as a quick toggle), `welcomePage.newFromTemplate` only the buttons. Unlike the setup checklist (#625), the card applies per project.

Test results (#763): The section “Test results” sits in the left column after “Project history” and shows, for each project of the “Projects” list, the last DUnitX run from the IDE (section `tests` of the project summary, #69): traffic light, badge “2 failed” or “all 57 passed” and “412 passed · 3 skipped · 18.4 s · 19:41”. A click selects the project; below it its failures are listed (`welcomePage.tests.maxFailures`) with message and file:line; a double-click opens project and test, “Run failed tests again” starts exactly these tests (`--run`), “In the debugger” the selected one (#585). With `welcomePage.tests.ci` Atlas reads server, job and multibranch from the `ci` section of the `.atlas` (#486) and queries Jenkins in the background when displaying (`/job/<Name>/lastCompletedBuild/api/json` and `…/testReport/api/json`, 5 s for both, per job at most every `welcomePage.tests.ci.intervalMinutes`). The second line “Jenkins #482 · 2 failed · 40 min ago · main” has its own traffic light, “green locally, red on server” is highlighted, server failures appear with the badge “Server” in the same list (double-click looks for the test in the test unit), “In browser” opens the build's page. If the server cannot be reached, the last state stays with “As of …”, without a dialog. If a new build turns red, the notification center reports it under “Build server”. User and API token are stored by *Store build server access …* (`Atlas.CiLogin`) in the Windows Credential Manager (target `Atlas:ci:<Server>`); it is sent only via https to the registered server.

Quick actions per project (#764): In “Projects” and in the “Recent” tab of “Continue working”, the row under the mouse or with keyboard focus shows the buttons from `welcomePage.quickActions.items`. “Open and build ▾” opens via `IOTAActionServices.OpenProject` (a new group asks about saving like *File › Open*) and builds via the build runner (#261, requester `welcome`, release guard #533) with the configuration and platform last used from the project summary; the selection reads configurations and enabled platforms from the .dproj. A group builds its projects one after another as configured. “Tests” takes the DUnitX test project next to the project or in `Tests\`, `Test\`, `..\Tests\`, `..\Test\` (for a group the group's test project), adds it to the open group if needed and starts “Run tests” (#69) with a build beforehand. “Launch profile ▾” sets the profile (#575) and starts with the debugger, “Pull” fetches in the background only fast-forward (`git pull --ff-only` or `svn update`, 2-minute time limit) and only without local changes. “Folder” opens Explorer, “Console” `welcomePage.quickActions.console` in the project folder (`wt.exe -d <Ordner>`, without Windows Terminal `cmd.exe`). Atlas intercepts Ctrl+B and Ctrl+T via `TApplicationEvents` before the IDE's keys, but only while a row of the welcome page has focus.

My issues (#765): The section “My issues · <Projekt>” (ID `atlas.issues`, order 26, right column; no fixed place in the Atlas layout because mockup L0 hides section ws12) shows at most 10 open issues assigned to me of the project selected in “Projects”, otherwise of the active one, otherwise of the topmost one. Provider, address and project are in the `tracker` section of the `.atlas` (#486), e.g. `"tracker": {"provider": "github", "url": "https://github.com", "project": "owner/repo"}` or `{"provider": "youtrack", "url": "https://firma.youtrack.cloud", "project": "ATL"}`; `issues.tracker` replaces the provider, `issues.query` the query. GitHub queries `GET /search/issues?q=<Abfrage> repo:<owner/repo> is:issue` (github.com via `api.github.com`, Enterprise via `<Server>/api/v3`), plus the open pull requests (a PR belongs to the issue if its branch contains the number as a separate piece or title or description say “closes/fixes/resolves #N”) and their check runs or combined status for the CI traffic light. YouTrack queries `GET <url>/api/issues?query=project: <Kürzel> <Abfrage>` with state, priority and sprint from the fields. The query runs when displaying, in the background thread, per project at most every 10 minutes (time in the `issues` section of the project summary, #592) with 5 s for the whole query; without a token in the Credential Manager there is no network access, without a network the last state stays with “As of …”. “Start” asks the version control (`TAtlasIdeVcs.Run`) about the kind and local changes (without unversioned files), asks for confirmation if there are changes and then creates via `IAtlasVcsBranching`: Git `git checkout -b <Branch> <Basis>` (base `issues.branchBase`, otherwise the project's main branch from `vcs.projects` or the `vcs` section of the `.atlas` (#1286), otherwise `main`, otherwise `master`; an existing branch only `git checkout`), SVN `svn copy ^/<Basis> ^/branches/<Name> --parents` (base as for Git, otherwise `trunk`) and `svn switch`. Afterwards Atlas opens the project via `TAtlasIdeProjects`. The current issue (remembered by “Start”, otherwise taken from the name of the current branch) appears as row `atlas.issue` in the status field (#591; short text of the tile “ATL-123 · 3 open”); a click ends it after confirmation. Prefix: as long as an issue is current and `issues.commitPattern` is not empty, Atlas prepends the prefix, once per dialog, to the first writable memo in the IDE's commit dialog (recognised by the active window with “Commit” in the class or component name). Under Git, after the first “Start”, Atlas asks once per project whether it may create the hook `prepare-commit-msg`; the hook reads the prefix from `<gitdir>/atlas-commit-prefix` (present only while an issue is current; “Finish” and switching off `welcomePage.issues` delete it) and leaves merge, squash and amend messages unchanged. Atlas never changes an existing third-party hook. The token is stored by *Store issue tracker access …* (`Atlas.TrackerLogin`) via `CredWriteW` under `Atlas:tracker:<Server>`; it is sent as “Authorization: Bearer” only via https to the API server (`TAtlasCiHttpTransport.CreateBearer`, redirects only to the same host).

Create branch (#1288): The dialog “Create branch” shows name (checked against Git's rules, note below the field, “Create” disabled), base, for SVN the message for `svn copy`, and under “What happens” the commands in plain text, exactly as Atlas will run them afterwards. Git: base `origin/<Hauptbranch>` (state of the last fetch), local main branch (default) or current branch; one step `git checkout --quiet --no-track -b <Name> <Basis> --`, nothing on the server. SVN: base `<Hauptbranch> @ HEAD` (the dialog asks the server for the revision in the background; until then “Determining HEAD revision …” and “Create” disabled) or the path of the working copy @ its revision; steps `svn copy ^/<Basis>@<Rev> ^/branches/<Name>@ --parents -m <Nachricht>` (marked “← on the server”) and `svn switch ^/branches/<Name>@ .`. If the working copy has `svn:externals`, the group “Externals (n)” (#1291) shows per row folder, source and a choice: “pin (r<N>)” (revision of the external's working copy), “unchanged” or “branch along”; externals with a fixed revision show “stays r<N>”, foreign repositories and file externals do not offer “branch along”. The preselection comes from the sub-item *Externals* of the *Version control* page: rules per source (`vcs.externals.rules`, one line “source = pin, keep or branch”, the longest matching prefix wins), then suggest “branch along” (`vcs.externals.suggestBranch`: with local changes, never, always), otherwise `vcs.externals.onBranch` (pin, keep, ask; with “ask”, “Create” stays disabled until every row is chosen). Atlas first copies packages that branch along next to their own trunk (location pattern under the package's project root, `^/Packages/Drucken/branches/<Name>`), then the project; from svn 1.9 and if everything is pinned, with `svn copy … --pin-externals`, otherwise Atlas rewrites `svn:externals` in the new branch itself (`svn checkout --depth empty` into a temp folder, `svn propset svn:externals -F`, commit with the branch's message; the other lines keep their format). Then it switches; svn fetches the branch's externals, and Atlas rebuilds the index. If the externals could not be read, only the note that they are copied along unchanged appears, as before.

Working copies (#1292): “Working copies …” in the project menu of the welcome page and in the Atlas menu opens a table with the root and every svn external or Git submodule, indented by depth. Columns: working copy, path in the repository (`^/Packages/Drucken/trunk`, for foreign repositories “other repository: <URL>”), revision (`r<N>`, for a fixed revision “r<N> · fixed”), changed and “New on the server” (empty until “Check server”; then `svn log -q --xml -r HEAD:<Rev>` per row). Atlas fills the rows one by one in the background (“determining …”). A double-click opens the folder in Explorer; the context menu offers “Update” (all), “Update only this one” (`svn update --ignore-externals` in the row's folder) and “Pin revision …” (asks first, sets `-r <N>` in `svn:externals` of the parent folder, without commit). For Git there is neither “Check server” nor “Only this one”. “Not saved” on the welcome page adds up the changes of all working copies and names each with its count. The quick action Pull follows `vcs.externals.update`: with externals (default), without (`--ignore-externals`) or ask (submenu “with externals”/“without externals”, the button shows ▾). The file watcher (#395) keeps the index of the changed files current after an update: it watches the project folder including subfolders and thus also the externals. With `vcs.externals.show = false` the menu item and the breakdown are missing, “Not saved” counts only the root as before. SVN options (#1290, group “SVN” on the *Version control* page): the location is a pattern (`vcs.branch.svn.location`, default `{projektwurzel}/branches/{name}`; `{projektwurzel}` is the part before `/trunk`, `/branches/<x>` or `/tags/<x>` in the path of the working copy, i.e. `^/Kasse` for `^/Kasse/trunk`; a pattern with `^/` applies as fixed). The dialog shows the resolved location in a field “Location” that follows the name until it is changed by hand; without a recognisable layout it stays empty with the note to specify the location; then the dialog also appears on “Start” with `vcs.branch.confirm` off. “Already exists” and switching to an existing branch in “My issues” search the same location; the main branch `trunk` also lies under the project root. Source (`vcs.branch.svn.source`): HEAD or the working copy with the highest revision from `svnversion`; with a mixed revision the dialog warns. “Afterwards” (`vcs.branch.svn.after`): switch (`svn switch`), fresh checkout (`svn checkout` into the folder from `vcs.branch.svn.checkoutFolder`, default `..\{projekt}-{kennung}` next to the working copy; afterwards Atlas asks whether the group or the project should be opened there) or nothing; both with a long time limit of 10 minutes. The message for `svn copy` comes from `vcs.branch.svn.message` (`{kennung} Branch für {titel}`; without an issue “Branch <Name>”). The dialog appears on “Start” in “My issues” as long as `vcs.branch.confirm` is on (with “Don't ask again, use defaults”), and always for the command “Create branch …” (command palette, `Atlas.CreateBranch`, current project) and in the context menu of a row of “Projects” on the welcome page. It runs in the background with the progress “Create branch 1/2: svn copy …” in the Messages view; if a step fails, it names that step with its cause and the steps that have already happened on the server and are not undone.

Git options (#1289, `vcs.branch.git.*`): The group “Git” in the dialog and on the *Version control* page determines what to branch from (state on the server with a preceding `git fetch`, local main branch, current branch), whether to push immediately (`git push --set-upstream`), what happens to open changes (take along, `git stash` with “Atlas: vor <Name>”, ask) and whether the branch is created in its own folder (`git worktree add`, folder pattern `..\{repo}-{kennung}`). If the fetch fails, Atlas asks “Branch from the local state?”; if only the push fails, the local branch remains. After a worktree Atlas offers to open the same project group or project from the new folder.

Issue preview (#1264, `issues.preview`): A click on a row or ID in “My issues” or the command *Show issue …* (`Atlas.IssueShow`) shows the issue in the dock window “Atlas issue” (`TAtlasIdeIssueWindow`, ID `AtlasIssue`, saved in the desktop); Ctrl+click opens the browser. GitHub queries `GET /repos/<owner/repo>/issues/<n>`, then the last page (if needed the one before) of `/comments?per_page=100` and `/timeline` for references; files `/user-attachments/files/` from text and comments appear as attachments that open in the browser. YouTrack queries `GET <url>/api/issues/<Kennung>?fields=…` once, including fields, tags, attachments, links and (with `issues.preview.comments`) comments. One query at a time in the background with 10 s; a new request and closing the window cancel it (`IAtlasCiCancel`). Images (at most 10, 8 MB) and attachments (64 MB) are downloaded by `IAtlasCiDownload` only via https from the token's server; other addresses are opened only by the browser (http/https without user). Attachments end up in `%TEMP%\Atlas\issues\<Kennung>\`; Atlas shows executable extensions only in Explorer. The last state is kept in memory (50) and as JSON in `%LOCALAPPDATA%\Atlas\issues\<Tracker>\<Kennung>.json` (7 days, without signed addresses) and appears immediately, without a network with “As of …”. The log names only provider, result and kind of error.

Issue IDs in code (#1265, `issues.codeLinks`): `TAtlasIdeCodeLinks` (`Atlas.IDE.Tracker.CodeLinks`) registers with `cevPaintLineEvents` (`plsEndPaint`) and `cevMouseEvents`. A timer (150 ms) fetches the tracker of the active project via a hook of the composition (`TAtlasIdeIssues.CodeTarget`, cached for 5 s) and, on a new buffer state (`TAtlasEditorSnapshots`), the states of all lines (`TAtlasCodeLinks.States`: comment `{ }` or `(* *)` open, directives do not count); only painting looks for the IDs of a line (`TAtlasCodeLinks.LineMatches`) and remembers them until the next state. The underline is drawn with `SetPixel`, every second pixel, two pixels above the bottom of the line in the accent colour, blended with the sampled background. Ctrl+left-click and right-click over an ID are intercepted by `TApplicationEvents.OnMessage` before the editor (as with the quick bookmarks #1104), which also swallows the release; Shift+right-click stays with the IDE. After 500 ms (`TAtlasCloseRules.TooltipShowDelayMs`, the same value as the Atlas tooltip) the hover asks `TAtlasIdeIssuePreview.Peek` (cache) and, if nothing is there or the state is older than 10 minutes, `Lookup` (background, without comments, identical requests once, “not found” remembered for 10 minutes; existing comments in the cache are kept). The pattern follows the IDE's active project (like *Show issue …*), not the project the file belongs to. Whether the Atlas tooltip stays silent over a comment is checked by manual test IK19.

Issues in the line history (#1275, `issues.blameLinks`): `TAtlasIdeBlameLinks` (`Atlas.IDE.Tracker.BlameLinks`) hooks into the line history via `TAtlasIdeLineChanges.SetBlameHooks`; the editor does not know the tracker. After every blame the line history fetches the full messages in the same background run (`IAtlasVcsLineHistory.Messages`: Git `log --no-walk=unsorted --format=… <Hashes> --`, SVN `log --xml -c r1,r2 <Datei>@`, 100 revisions each), because Git blame only delivers the first line and SVN blame no message at all. The margin display appends the IDs (pattern as in #1265) after the time; nobody queries the tracker when painting. The line history's hover gets one link row per ID (`Peek`, otherwise `Lookup` as with the IDs in code) and the link “Issues for this method (n)”; the number is computed by a background run once per method and state of the working copy (`ChangeMarker`). Ctrl+click and right-click on the margin display are intercepted by `TApplicationEvents.OnMessage` (`TAtlasIdeLineChanges.BlameAt`: same window, same top line, taken-over line). Code templates (#51): At the start of a statement, templates with the badge `sn` and the label “Snippet” appear in the list: `tryf` (try…finally with Create/Free), `trye`, `forin`, `fori`, `while`, `repeat`, `class`, `record`, `prop`, `propset` (setter with change check and `Invalidate`), `comp` (component skeleton) and `reg` (Register procedure). Enter inserts the template with the line's indentation and selects the first placeholder; typing replaces it, placeholders with the same number change along. Tab jumps on, Shift+Tab back, after the last one to the end position; Enter jumps there and finishes, Esc finishes in place. The current placeholder is framed, linked ones dashed, followed by “Placeholder 1 / 2 · Tab next · Esc done”. Your own templates are stored as `*.atlas-snippet` in `%APPDATA%\Atlas\Snippets` (Atlas rereads the folder when it changes; it skips faulty files) and replace supplied ones with the same prefix:

```
name: Liste anlegen
prefix: lst
description: TStringList mit Freigabe
---
${1:Items} := TStringList.Create;
try
  $0
finally
  ${1}.Free;
end;
```

`${1:Name}` is a placeholder with a default, `${2}` one without, `$0` the end position; `$FF` and other hex numbers remain text. Switch off under *Tools › Options › Third Party › Atlas* (“Offer code templates (snippets) in the list”, registry value `Snippets`).

`$$` stands for a `$` in the text. Inserting and filling in together are one undo step: Ctrl+Z after finishing reverts the whole template.

The IDE's Live Templates (`*.xml` under `%APPDATA%\Embarcadero\BDS\<Version>\code_templates`) also appear in the list; points become placeholders, `|end|` the end position, scripts are dropped. Switch off with “Import the IDE's Live Templates as code templates” (registry value `ImportIdeTemplates`). With the same prefix: your own template before IDE template before supplied one.

Your own templates can be edited under *Tools › Options › Third Party › Atlas.Snippets*: the list shows all templates with their origin; “New” creates your own, “Copy as own” turns a supplied or IDE template into your own that replaces it, “Delete” removes your own. Prefixes must be unique; “OK” saves the files in `%APPDATA%\Atlas\Snippets`.

In addition, the server supplies templates that know the class. They appear only if the line contains nothing except the typed word:

- `prop` in a class declaration, per field `FName` without property: inserts `property Name: Typ read FName write SetName;`, declares `SetName` in the private section and creates the body.
- `changed` in the empty body of a setter: `if FName <> Value then begin FName := Value; Invalidate; end;`.
- `create` in the constructor: creates the object fields not yet created (components with `Self` as owner), preceded by `inherited;` if it is missing.
- `free` in the destructor: frees the fields created in the constructor in reverse order with `FreeAndNil`.

The setter looks the same everywhere, whether it comes from `prop`, `changed`, `propset`, `/prop` or `/changed`: for controls with `Invalidate`, otherwise with `Changed` or `DoChange` if the class has one of them. With “Offer code templates (snippets) in the list” off these templates are missing too.

Postfix templates (#188): After an expression and a dot, the list offers templates that transform the expression; they carry the label “Postfix” and come after all real members. Filtering uses the prefix, so `FKunde.nn` finds `notnil`. Only what fits the type is offered:

| Prefix | Result | Type |
|---|---|---|
| `for`, `forin` | `for var Item in Liste do` | array, set, type with `GetEnumerator` |
| `tryf` | `try … finally Obj.Free; end;` | class |
| `ifa`, `notnil` | `if Assigned(X) then` | class, interface, pointer |
| `nil` | `if not Assigned(X) then` | class, interface, pointer |
| `not` | `not B` | Boolean |
| `if` | `if B then` | Boolean |
| `fmt` | `Format(S, [])` | string |
| `free` | `FreeAndNil(Obj);` | class |
| `try` | `var Foo := TFoo.Create; try … finally Foo.Free; end;` | constructor call |
| `var` | `var Name := X;` | any expression |
| `exit` | `Exit(X);` | in a function |

Statements (everything except `not` and `fmt`) are only available if the expression starts the line. The expression extends to the start of the statement, also across calls and typecasts (`GetKunde(1).notnil`, `TFoo(Obj).free`), not across lines. After a header such as `if … then` the cursor is placed indented on the following line; variable names (`Item`, `Foo`) are placeholders as with the code templates. Without inline variables (Delphi before 10.3 or `refactoring.inlineVar` off) the result is `for Item in Liste do` and `Foo := …;` with an entry in the routine's `var` section; then only if the type is known.

Your own postfix templates are `*.atlas-snippet` files with two more header lines; `$expr` stands for the expression:

```
name: Protokollieren
prefix: log
postfix: true
type: class
---
Log.Debug('%s', [$expr.ClassName]);$0
```

`type:` is a trait (`any`, `reference`, `class`, `string`, `boolean`, `enumerable`, `constructor`, `function`) or a type name; then the type itself and every descendant matches. Without `type:` every expression matches. Switch off with `completion.postfixTemplates` in `atlas.json` (*Tools › Options › Third Party › Atlas*, page Completion); “Offer code templates (snippets) in the list” does not affect the postfix templates.

Crash safety (#493): No error in Atlas reaches the IDE. Keyboard bindings, editor and compile notifiers, painting, timers, menu, options pages and background threads run through a common guard; errors go, without a dialog, to the log `%LOCALAPPDATA%\Atlas\Logs\atlas.log` (rotating, 5 × 1 MB; per line Atlas version, feature or source, error class and a shortened single-line message, below it the call chain with unit, routine and line from the map file next to the BPL). Three errors within five minutes switch off only the affected feature or data source (such as “Completion (XMLDoc)”, the other sources keep delivering), with a warning in the Messages view and an entry in the notification center (“Switch on again”, “Open log”); every visible feature has its own safeguard for this, and the same error counts only once within one second. *Tools › Options › Third Party › Atlas* shows at the bottom what is switched off and switches it back on individually or all at once; so does the Atlas menu. Data sources called by the main thread (completion, parameter hint) have a hard time limit (default 200 ms, field “Time limit for data sources”, registry `ProviderTimeLimitMs`, 50 to 5000); if one takes longer, Atlas aborts. That does not count as an error: the log names the slow source at most once per minute, and as long as its previous call is still running, it is skipped. Errors and time limits of the server itself do not count; for those there are the server's restart and time limit. If the server ends by itself, the log names the cause from the exit code (such as “Stack overflow (0xC00000FD)”), the run time, the last and the still open requests; the status field shows the cause. What the server writes to stderr is stored in `%LOCALAPPDATA%\Atlas\Logs\server-stderr.log` (one header line per start, moved to `server-stderr.1.log` at the next start from 1 MB). The next request restarts after the first crash; if the server ends twice with the same cause within ten minutes, Atlas no longer restarts it by itself but offers “Restart server” and “Create bug report…” in the notification center; the bug report then contains the end of server-stderr.log. When the IDE closes and when the package is unloaded, Atlas first sets a common cancellation signal: running requests to the server, watchdogs and time-limit workers stop waiting immediately, the server is terminated after 400 ms at the latest, and all threads end within one second; the duration is in the log. Atlas reads and writes editor buffers only in the main thread; background threads work on copies.

Baseline for legacy projects (#97): *Update project baseline* in the command palette (`Atlas.UpdateBaseline`) records all of today's rule findings of the active project in `atlas-baseline.json`; afterwards the editor and `AtlasServer --check` only show new findings. If the baseline has entries whose file is missing (renamed, moved or deleted), Atlas names them with their path beforehand and asks; they drop out on update. The running server then checks all files of the project in the background (`atlas.updateBaseline`), writes the file into the workspace folder and reports in the Messages window the removed entries without a file and the counters (“Baseline written: … (412 findings, 87 files checked; 3 new, 5 removed, 409 unchanged)”). For large legacy projects this takes a few seconds to minutes, during which the server answers nothing else; the time limit is 10 minutes. Can be switched off with `baseline.update` (page *Editor*, quick toggle); then only the command disappears, the baseline keeps working. After every build and after updating, the plugin stores the state in the `baseline` section of the project summary (present, entries, findings, entries without a file, last update with new and removed), for project history (#758) and setup (#759). The *Server* page of the options still updates via the command line. Compiler messages in the baseline (#530) are kept when updating.

Running DUnitX tests (#69): In a test unit, after `[TestFixture]` there is the badge “Run tests of the class” and after every `[Test]`/`[TestCase]` “Run test” (like the test unit lens at the end of the line, because the IDE cannot insert a line of its own); a click starts the test, after the run the badge shows “passed” or “failed”. *Run tests* and *Run failed tests again* are in the command palette. Atlas takes the test project of the test unit, otherwise the active one or the only one in the project group whose main file uses `DUnitX.TestFramework`, with its configuration and platform (Windows platforms only); with “Build before tests” (default) it builds beforehand like `build_project`, otherwise it starts the existing EXE. The EXE runs without a window with `--exitbehavior:Continue --xmlfile:…`; the test program must create DUnitX's XML logger (`TDUnitXXMLNUnitFileLogger`, like RAD Studio's project template). Failures appear as a problem at the method header with expected and actual value and as a clickable line in the Messages view (group “Atlas”); the result goes into the project summary (Tests card #763). Can be switched off with “Run DUnitX tests” (Options › Atlas › Compiler, quick toggle) and “Code lens “Run test”” (page *Editor*); “Run tests automatically after a successful build” is initially off.

Project file `.atlas` (#486): Plugin settings for everyone in the team are stored in `.atlas` in the folder of the .dproj, in a folder above it up to the root of the repository (`.git` or `.svn`; without a repository up to the folder of the opened .groupproj) or next to the .groupproj, and are checked in; personal settings under *Tools › Options › Atlas* remain separate, and a value from `.atlas` takes precedence. *Open project file .atlas* in the command palette (`Atlas.TeamFile`) creates the file with a skeleton (version 1, examples as comments) and opens it. Content: prefixes (`naming`), folders with project templates (`snippets`, in completion before your own), format functions, SQL targets, file methods, main-thread exceptions, launch profiles, build server (`ci`) and issue tracker (`tracker`). Atlas ignores credentials, absolute paths and paths outside the repository; user and token belong in the Windows Credential Manager. Atlas checks every 2 s whether the project or the file has changed; errors and ignored entries appear once in the Messages view. The *Project file* area of the options page shows each value with “from .atlas”; can be switched off there and as a quick toggle.

Launch profiles (#575): A profile bundles parameters, working folder, environment variables and host application. *Launch profile: …* in the command palette (`Atlas.StartProfile`) or a click on the field “Launch profile: <Name>” in the editor's status bar opens the selection for the active project: first the shared profiles from `startProfiles` of the project file `.atlas` (they win if the name is the same), then the personal ones. Atlas writes the values into the active configuration and platform, i.e. where *Run › Parameters* stores them too; *Run* (F9) and *Run Without Debugging* then use them. Relative paths apply from the folder of the `.atlas` or, for personal profiles, from that of the .dproj; macros like `$(BDS)` are kept; the environment variables add to those of the IDE (`$(Debugger_EnvVars)`). Atlas remembers the active profile per project and sets it again when project, configuration or platform change, but only if a value differs (otherwise the project would count as modified). It also remembers the launch options from before the first profile; “No launch profile” restores them. Personal profiles are created by “Save current launch options as personal profile …”; they, the active profile and the remembered launch options are stored only locally in `%LOCALAPPDATA%\Atlas\startprofiles\<Schlüssel>.json` (JSON, “Edit personal launch profiles” opens the file). Because the IDE saves the set values with the .dproj, they end up there too at the next save. Can be switched off with “Launch profiles” and “Launch profile in the status bar” (Options › Atlas › Compiler, both quick switches).

Debugging a single test (#585): Next to “Run test” of the code lens there is “Debug”; *Debug test at cursor* or *Run test at cursor* in the command palette and “Debug test”/“Run test” in the editor's context menu apply to the test in whose attribute, declaration or body the cursor is (at `[TestFixture]` for the whole fixture, on the line of a `[TestCase]` only for that case). Atlas builds the test project, temporarily sets the launch parameters `--run:Unit.Fixture.Methode --exitbehavior:Continue --xmlfile:<temp>` (your own parameters stay in front), makes it the active project and starts it with *Run*; with *Options › Atlas › Debugging › Stop at the start of the method when debugging a test* the debugger stops on the method's first statement (a one-off breakpoint that Atlas removes after the first stop; your own breakpoint there remains). When the program ends, active project and launch parameters are as before and the result appears at the tests as after “Run tests”. If the test unit belongs to several test projects, Atlas asks once and remembers the choice. Can be switched off with “Debug test” (page *Debugging*, quick toggle); without “Code lens “Run test”” there are no badges.

Check before compiling (#529): With `build.gate` = warn or block (*Tools › Options › Atlas › Compiler*) Atlas checks, before every make and build started by the user, the project's units that have changed since the last successful compile (a different state than at the last successful compile of the session, otherwise newer than the output file). The check runs via the running server with the text of the buffers, even unsaved; syntax errors and rule findings with severity error count, no warnings and no compiler messages of the previous build. The findings appear in the Atlas group of the Messages window (double-click jumps there). warn compiles anyway, block aborts; a second compile without changes within 10 s runs (deliberate override). The whole check may take `build.gateTimeoutMs` (default 300 ms); after that the compile runs unchecked, and a note about it appears once per session. Not checked are Code Insight, the background check (#548), syntax check, clean and jobs from Claude Code; without a running server Atlas does not check.

Gate for hints and warnings (#530): After every build by the user with readable messages, Atlas evaluates the result itself (`Atlas.Core.Build.Verdict`) and writes a summary into the Atlas group of the Messages window, e.g. “Build Kasse succeeded, but 2 warnings, 1 hint”, below it the first relevant message (double-click jumps there). The group stays in the background; the IDE's “Build” tab stays in front. With `build.zeroHints` (*Tools › Options › Atlas › Compiler*) a build with warnings or hints counts as failed: the summary reads “Build Kasse counts as failed: 1 hint (build.zeroHints)”, Atlas brings the group to the front, the notification center shows a red entry with “Go to message”, and tests after the build (#69) do not run. `build.warningsAsErrors` names codes like `W1035, H2164` that act this way, independently of `build.zeroHints`. `build.summary` switches off the summary; Atlas still reports a build that the gate fails. Known legacy issues: *Add current compiler messages to the baseline* (command palette, `Atlas.CompilerBaseline`) takes over the warnings and hints of the last build of the active project via the server into `atlas-baseline.json`, the same file as the rule findings (#97); afterwards only new messages count, and the summary names the others as “(3 more in the baseline)”. Per unit the command replaces its previous entries; units that a make did not recompile keep theirs (for a complete state run *Build* first). Without a running server all messages count. The command can be switched off with `baseline.update`.

Switching off a compiler warning selectively (#531): If the cursor is on a line with a warning or hint from the last compiler run, the code actions menu (Ctrl+.) offers “Disable W1000 here ({$WARN SYMBOL_DEPRECATED OFF})”, “Disable W1000 in TKasse.Buchen”, “Disable W1000 in the whole unit” and “Disable W1000 in the whole project (project options)”. Atlas asks for a reason (empty allowed, `refactoring.disableWarningReason`), writes it as `// …` after the OFF switch and inserts both switches in one undo step. Hints get `{$HINTS OFF}`/`{$HINTS ON}`; warnings whose number Atlas cannot map to an identifier (or that the project's Delphi version does not know yet) get `{$WARNINGS OFF}`/`{$WARNINGS ON}`, which switches off all warnings in between – Atlas says so in the title and in the Messages window. Flow messages like H2164 (variable never used) or W1035 (function without result) are checked by the compiler only at the end of the routine; for them the routine is the preferred action, and there is no action around the line. The project variant asks for confirmation and enters `DCC_<Bezeichner> = false` in the base configuration (like *Project › Options › Compiler Messages*); the project then counts as modified. Can be switched off with `refactoring.disableWarning`.

Quick fixes for compiler messages, part 2 (#549): On a line with one of the following messages from the last compiler run, the code actions menu (Ctrl+.) offers a fix, the preferred one first. H2443 (inline function not expanded): “Add uses System.Generics.Collections (H2443)”; the unit is in the message, and Atlas adds it to the uses of the line's section. E2003 (undeclared identifier): “Add uses System.Classes (E2003: TStringList)” for every unit that declares the identifier, RTL and VCL units first; if the cursor is already on the identifier, the usual uses action applies. H2077 (value never used): “Remove ineffective assignment to X” if the right-hand side consists only of literals, operators and local names; for a call with parentheses “Remove assignment to X, only call Foo”; for a name without parentheses (it could be a function) no fix. W1035 (return value undefined): `Result := Default(<Typ>);` right after the begin. W1057/W1058 (implicit string conversion): `string(…)` or `AnsiString(…)` around the right-hand side of the assignment or, if the message carries a column, around the argument there. If the same message occurs several times in the file, “Fix all W1057 in the file (n)” combines them all in one undo step. Can be switched off with `refactoring.compilerFixes`.

Unit not found (#550): On a line with F2613 (“Unit not found”) or F1026 (“File not found”) from the last compiler run, Atlas searches for the unit, in this order: in the project folder and its subfolders (up to depth 4), in the folders and search paths of the other projects of the group, in the search paths of the project's other configurations and platforms, in the library paths of other platforms and in the index. Folders the compiler has already searched do not count. For a find, the code actions menu (Ctrl+.) offers “Add folder Source\Common to the search path of Debug” (preferred), “… of all configurations” and, for a source, “Add Werkzeug.pas to the project”. The path is relative to the `.dproj`; Atlas adds it via the IDE's project options at the front of `DCC_UnitSearchPath` (a configuration without its own value keeps what is inherited with `$(DCC_UnitSearchPath)`); the project then counts as modified. If the folder comes from another configuration or another project, the title says so (“is in Debug, Win32”). If the unit only exists in the library of other platforms, the only action is “Winapi.Windows does not exist for Linux64 (only Win32, Win64)”; without a find, “… not found: show searched locations” shows the locations searched. Can be switched off with `refactoring.missingUnit`.

Release build guard (#533): Before make and build in a release configuration (“Release” or in `build.releaseConfigs`), Atlas checks the project options as the IDE uses them for this build (even unsaved): symbol DEBUG, debug information, stack frames, assertions, range and overflow checking, `ReportMemoryLeaksOnShutdown := True` outside `{$IFDEF DEBUG}`, missing or unchanged version information and an output folder as in Debug. Findings appear in the Atlas group of the Messages window with rule ID and the path to the option; with `build.gate` = block the build aborts, a second build within 10 s runs anyway. *Check release build* in the command palette (`Atlas.CheckRelease`) checks without building. Settings in the *Release build* area under *Tools › Options › Atlas*; every check can be switched off individually, the compiler options with a target value.

If there is a problem under the mouse, the tooltip shows it at the top; for rule findings, the confidence (high, medium, low) appears below it as a separate line (#144).

For troubleshooting: set the value `Diagnose` (DWORD) = `1` under `HKCU\Software\Atlas\IdePlugin` and restart the IDE. The plugin then writes every call from the IDE (hover, Ctrl+click, position and result) to a file next to the BPL with the same name, e.g. `Atlas.IDE.Expert370.log`. The file contains no paths, file or identifier names (only extensions, positions and lengths) and may be passed on. For completion it also records how long the server took, whether it did not answer and why the popup closed.

If the server finds no definition, nothing happens on Ctrl+click. The server finds declarations in include files (`{$I …}`) only with the include resolver (#264).

Under Delphi 12 the tooltip closes via Atlas's keyboard hook, because the code editor there does not report keyboard events; otherwise the plugin behaves as under Delphi 13.

- If a symbol without a source is similar to a known one, Atlas suggests it (typo).

## Built-in LSP client

RAD Studio 13 can integrate third-party language servers (LSP) via stdio. This way the Atlas server replaces the built-in Code Insight server for Delphi files.

## Prerequisites

- RAD Studio 13 (registry version `37.0`)
- `AtlasServer.exe` in a fixed location, e.g. `C:\Tools\AtlasServer.exe`. The file is locked as long as the IDE keeps the server running. For an update, close the IDE or rename the old file and put the new one next to it.

## 1. Create the server in the Code Insight manager

*Tools > Options > Editor > Language > Code Insight > Code Insight Manager > New*

| Field | Value |
|---|---|
| Name | `Atlas` |
| Executable | path to `AtlasServer.exe` |
| Command line parameters | empty, or for troubleshooting `--log C:\Temp\atlas.log --log-level debug` (anonymised: paths and names as `datei#N`/`name#N`; `--log-names` writes them in plain text) |
| Language identifier | any (see step 2) |
| Timeout | `15000` |
| InitializationOptions | `{}` |

## 2. Switch the language to Delphi (registry)

The language list in the dialog offers neither `delphi` nor `pascal`. Therefore the entry is created with any language and the language is changed in the registry afterwards. The IDE must be closed while doing so.

```
HKEY_CURRENT_USER\Software\Embarcadero\BDS\37.0\LSP\UserDefined\Atlas
  LanguageId = Delphi
```

After that, “Atlas” is available for Delphi in the Code Insight manager. The selection is stored here:

```
HKEY_CURRENT_USER\Software\Embarcadero\BDS\37.0\Editor\Source Options\Borland.EditOptions.Pascal
  Insight Manager = Atlas
```

## 3. Verify

1. Restart the IDE and open a `.pas` from a project.
2. The log (with `--log`) should contain these lines:
   - `Kein Arbeitsbereichsordner gemeldet; Ordner werden aus den geöffneten Dateien abgeleitet`
   - `Arbeitsbereichsordner: <Ordner mit der .dproj>`
   - `Symbolindex für … fertig in … ms`
3. Hover over an identifier. The tooltip shows the declaration.

## Behaviour of the RAD Studio client

- **No workspace:** The IDE reports `rootUri` as `file:///` and no `workspaceFolders`. The server therefore derives the workspace from every opened file: it takes the nearest folder above it with a `.dproj` or `.groupproj`.
- **Plain text only:** The IDE cannot handle Markdown (`hover.contentFormat = ["plaintext"]`). The server therefore delivers hover as plain text.
- **Restarts:** Every started IDE starts its own server. The default “Restart server each time a project is activated” additionally restarts it on every project change. The IDE terminates the server hard, without `shutdown`/`exit`. The log therefore lacks the line “Beendet mit Exit-Code” (“Exited with exit code”). That is not a crash. Since #175 the next start logs “N frühere Serverläufe ohne Endzeile (von der IDE beendet oder abgestürzt)” (N earlier server runs without an end line, terminated by the IDE or crashed); if the IDE only disconnects, “Verbindung beendet: Eingabe geschlossen ohne exit (IDE hat die Verbindung getrennt)” (connection ended: input closed without exit, the IDE disconnected) appears before “Beendet mit Exit-Code 0”. A real crash is shown by “Server abgebrochen” (server aborted) with the error class; the diagnostic log under `%LOCALAPPDATA%\Atlas\Logs\Diagnose` records the same as `run end reason …`.
- **Completion:** The server reports `completionProvider` and answers `textDocument/completion` (#31). The IDE reports `completion.completionItem.documentationFormat = ["plaintext"]`; the documentation in `completionItem/resolve` then comes as plain text (whole XMLDoc text), to clients with Markdown as `MarkupContent`.
- **Language ID:** In `didOpen` the IDE sends `languageId = "pascal"`. The server does not evaluate `languageId`, so this is harmless. The protocol recording `Tests/Data/Protocol/rad-studio-client.json` replays exactly this client (`rootUri` `file:///`, plain text, `pascal`).

## Troubleshooting

- `--trace <Datei>` records the JSON-RPC traffic. The file is recreated at every start. If it is in use because another IDE already has a server running, the server writes to `<Datei>-<PID>.<Endung>` and names the file in the log.
- A crash appears in the log with a stack trace. If only the line “Beendet mit Exit-Code” is missing from the log, the IDE terminated the server.
