# IDE comfort

Back to the [README](../../../README.md)

- **Atlas welcome page** on the IDE welcome page (as single sections or as one “Atlas” section on top, switchable with `welcomePage.ideWelcomePage`) and, independently, in the dockable window *Atlas Start* (*View › Atlas Start*, command palette; opens when the last project is closed and, with `welcomePage.openOnStart`, on IDE start) with sections: continue working, projects with quick actions, project history, unsaved, project setup, test results, my issues, new in Atlas, discover Atlas, help and feedback; search box and free layout
- **Issue tracker** (GitHub, YouTrack): "My issues" on the welcome page, start an issue with branch and commit prefix; all tracker settings live under `issues.*` on their own page *Tools › Options › Atlas › Issue tracker* (earlier `welcomePage.issues.*` values are taken over on first start); several tracker connections side by side (`issues.connections`) with token state and "Check", the token only in the Windows credential store; issue preview in the dockable window *Atlas Issue* (`issues.preview`: click an issue in "My issues" or run *Show issue…*) with description as Markdown, fields, comments, attachments, linked issues, back/forward and a 7-day offline cache; personal assignment of Delphi projects, project groups or folders to a connection and tracker project (`issues.projects`, the `.atlas` wins), with "No tracker for this project – assign …" in "My issues"; several named queries (`issues.queries`, per connection and tracker project) with a picker and hit counts in the "My issues" header (`issues.queryPicker`), the earlier single query becomes "Standard"; issue keys such as `ATL-123` or `#42` in comments get a dotted underline, a short preview on hover, Ctrl+click into the preview and their own right-click menu (`issues.codeLinks`); the line history shows the issue keys of the commit message, its hover adds title and state per key, Ctrl+click opens the preview, and *Issues for this method* lists every issue whose commits changed the method (or unit) at the cursor, with commit count and diff (`issues.blameLinks`, Git `log -L` and SVN); "Edit query" dialog with templates (YouTrack in German and English) and "Test", which names the cause (no token, rejected, unknown project, query rejected with the tracker's message, unreadable answer) and the query actually sent; "Check" detects a German YouTrack interface and the default query follows it; "Create issue …" from the editor (selection or TODO under the cursor, location, method, branch, code snippet as its own checkbox) and from findings of the Atlas check, with a preview before sending; afterwards `// TODO ATL-130: …` in the code and the key on the clipboard (`issues.create`, `issues.create.includeCode`); with `issues.syncState` "Start" sets state, assignee and a comment in the tracker, "Finish" opens a dialog with target state, comment ({branch}, {commits}, {pr}) and hand-over, and the preview gets a comment box (Ctrl+Enter); with `issues.timeTracking` Atlas tracks working time per issue (status field "ATL-123 · 1:25", idle time stops the clock, pause, correct, *Open time bookings…*) and offers to book it as a YouTrack work item when finishing (rounded, work type, text from the commits; GitHub as a comment); checklists (`- [ ]`) can be ticked right in the preview, with progress "3/5" in the header and the status field (`issues.preview.checklists`, `issues.checklistStatus`); dependencies and subtasks as a tree (`issues.preview.links`: depends on, blocks, subtasks with progress 2/3, create a subtask or add a link right from the preview) and a warning on "Start" while a blocking issue is still open (`issues.warnBlocked`); a board in the dockable window *Atlas Board* (`issues.board`: the current sprint of the YouTrack agile board or the GitHub project as columns with cards, "Only mine", search, dragging changes the state in the tracker after a confirmation, click opens the preview, double-click starts the issue); a *Sprint* section on the start page (`welcomePage.sprint`: current sprint with days left, own numbers, "team left" and a burndown, compared with the previous sprint plus the velocity of the last three sprints; clicking the numbers filters "My issues"); search issues from the command palette (`issues.paletteSearch`: `#text`, `#42` or `ATL-12`; Enter preview, Ctrl+Enter start, Shift+Enter browser, Ctrl+C copy key; an empty `#` lists recently opened issues); a richer comment editor (`issues.commentEditor`) in the preview and the finish dialog: `@` suggests tracker users, `#` and `ATL-` suggest issues, Ctrl+B/Ctrl+I/Ctrl+Shift+K format, a preview tab, text snippets with {branch}, {commit}, {issue} and {version} (`issues.commentSnippets`) and drafts kept per issue, plus a *Development* tab (`issues.preview.development`) with the issue's branches (ahead/behind, switch), commits (diff, jump to the change), pull requests with CI light (GitHub) or YouTrack VCS changes, and the changed units grouped by project; notifications about my issues (`issues.notify`): new comments, assignments and state changes in the notification center, "Open" jumps to the new comment, a dot in "My issues" until opened; *Attach to issue…* (`issues.attach`: Atlas menu, command palette, preview window, status field) sends a screenshot of the running program or of the form in the designer (with rectangle, arrow and blacken), a log file (last N lines), a debug note and the exception history in one step: YouTrack gets the files as attachments plus a comment, GitHub gets texts as a comment and images via the clipboard
- **Version control** (Git, SVN): own page *Tools › Options › Atlas › Version control* (#1285) with the kind (`vcs.provider`: automatic, Git, SVN, off), a custom path to git.exe or svn.exe (`vcs.git.path`, `vcs.svn.path`, empty = PATH and the usual folders; a custom path is used alone, and if the file is missing Atlas says so instead of taking another program), "Check" with version and location, a time limit per call (`vcs.timeoutSeconds`) and the state of the current project (working copy, branch or path, revision, where the setting comes from); the values also apply to `atlas --changed`. The table *Projects* (#1286, `vcs.projects`) sets kind and main branch per `.dproj`, `.groupproj` or folder (e.g. one row per package folder from SVN externals); the `vcs` section of the `.atlas` wins, then the row for the `.dproj`, the open project group, the longest matching folder (the same order as the tracker assignment). Change markers use the row of the unit's folder; "Start" in *My issues* branches from the main branch and incoming commits fall back to it. The table *Servers* (#1287) checks on click whether Atlas reaches the server without prompting (`git ls-remote`, `svn info ^/`, 10 s): reachable, sign-in needed, not reachable, no server; *Sign in …* opens a console where Git Credential Manager or SVN ask and store the sign-in, Atlas stores no credentials. Fetch, pull and push never prompt (`GIT_TERMINAL_PROMPT=0`, `GCM_INTERACTIVE=never`); a missing sign-in shows up in *Continue working* as "Server sign-in needed – check …" instead of an empty list. *Create branch …* (#1288; command palette, context menu of *Projects*, and "Start" in *My issues* while `vcs.branch.confirm` is on) shows name, base (Git: origin/main, local main, current branch; SVN: main branch @ HEAD with the revision from the server, or the working copy @ its revision), the SVN commit message and under *What happens* the exact git/svn commands Atlas then runs, steps that change the server marked; svn:externals are pointed out; SVN branches go next to the project's trunk (#1290, `vcs.branch.svn.location`, default `{projektwurzel}/branches/{name}`, so `^/Kasse/trunk` gets `^/Kasse/branches/<name>`), with source (HEAD or the working copy, warning for a mixed revision), what happens next (switch, fresh checkout into a folder next to it, which Atlas then offers to open, or nothing) and the commit message (`{kennung} Branch für {titel}`); the group "Externals (n)" (#1291) lists every `svn:externals` line with folder and source and lets you pin it to the revision of its working copy, leave it unchanged or branch it along (the package is copied next to its own trunk, e.g. `^/Packages/Drucken/branches/<name>`, and the external line in the new branch is rewritten through a slim checkout); externals with a fixed revision stay, externals from other repositories and file externals are never branched along; defaults on the *Externals* node (`vcs.externals.onBranch`: pin, keep, ask; `vcs.externals.suggestBranch`: with local changes, never, always; `vcs.externals.rules`: one rule per source, the longest match wins), pinning uses `svn copy --pin-externals` from svn 1.9 when everything is pinned, and after switching Atlas rebuilds the index; "Working copies …" (#1292, project menu of the welcome page and the Atlas menu) shows the root, every svn external and every git submodule with path in the repository, revision ("· fixed" for pinned externals), changes and, on "Check server", the new commits; double-click opens the folder, the context menu updates all, only this one or pins the revision (asks first, no commit); "Unsaved" names each working copy with its changes, Pull gets a submenu "with/without externals" (`vcs.externals.show`, `vcs.externals.update`: with, without, ask). Git options for creating branches (#1289, `vcs.branch.git.*`, group *Git* on the page and in the dialog): base `remote` (default; `git fetch <remote> <main>` first, if that fails Atlas asks after the dialog "Branch from the local state?" with the server state, without the dialog it stops), `local` or `current`; `push` `later` or `now` (`git push --set-upstream`; if only the push fails the local branch stays and the message names the reason); uncommitted changes `carry`, `stash` (`git stash push --include-untracked -m "Atlas: vor <name>"`) or `ask` (carry over, stash, cancel); `worktree` creates the branch in its own folder (`git worktree add`, `worktreeFolder` with `{repo}`, `{name}`, `{kennung}`, default `..\{repo}-{kennung}`) and then offers to open the same `.groupproj`/`.dproj` from there; an existing folder is refused. With `local`, `later`, `carry` and no worktree everything works as before.
- **Command palette** (Ctrl+Shift+P) for all Atlas commands
- **Atlas status field** with index progress and quick toggles (Ctrl+Shift+Alt+A)
- **Atlas server window** (#1356, `server.statusWindow`; *Atlas › Help and diagnostics*, command `Atlas.ServerStatus`, click on the *Server* line of the status window, double-click on the status in the Atlas status bar): process, version, uptime, state (loading, ready, checking) and restarts of the session; memory per area (symbols, usages, library units, syntax trees, open documents, rest) as bars against the budget with the hint “usages are being offloaded”; the 10 slowest units and rules of the last check run, the slowest requests, queue and cache hits; double-click opens the unit or the rule settings. It reads the status the status lines fetch every 5 s anyway and only while visible; *Refresh* asks at once, *Rebuild index*, *Create diagnostic package …* writes a ZIP with the bug report (#108), status, the session log and, with `--trace`, the trace of the last minutes, anonymised like the bug report and never with credentials, after a preview
- **Notification centre** (Ctrl+Shift+Alt+N) collects messages from builds, checks and the server
- **Change marks** in the gutter against Git HEAD or SVN BASE
- **Find selection** with F3 or Shift+F3
- **Silent reload** of files changed outside the IDE
- **Robustness:** no error in Atlas reaches the IDE, hang watchdog with log, stack traces with unit and line for every caught error, check rules and editor features handle arbitrarily deeply nested expressions without recursion (a unit beyond the 100000-level net gets the hint `unit-too-deep` instead of silently losing its findings), a feature that keeps failing is switched off on its own (with a notification to switch it back on) while the others keep running, server crashes are logged with their cause (exit code, stderr) and a server that crashes the same way twice is not restarted in a loop, safe start after a crash (a slow IDE start is not a crash: instead of switching features off next time, Atlas names how long it held up the start and which of its parts took longest), its own data files (favorites, histories, bookmarks, notes …) are replaced in one step, and a damaged one is kept next to it as `.defekt` instead of being silently overwritten, bug report to attach, key conflicts with other extensions (GExperts, CnPack, MMX) are detected, every crash of a request in the server is saved as a reproducible case (`%LOCALAPPDATA%\Atlas\crash`: request, recent messages, snapshot of the file, settings without credentials, call stack, `wiederholen.cmd` for `AtlasServer --replay`; `Tools/New-CrashTest.ps1` turns it into a DUnitX test), the notice after the restart names method, file, line and exception with “Open case” and “Create issue”, and as a safety net the server skips a request that crashed twice on the same unchanged file, visible in the status bar and the problems window (`server.crashCases`, `server.crashSkip`)
- **Update check** only after consent
- **Accessibility:** lists and tooltips readable by UI Automation
